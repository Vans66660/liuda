# 团队近期任务

> 记录 App 方向和早期小程序工作包。当前运行方式与功能状态见 [仓库首页](../README.md)。

## 当前优先级（2026-11-06）

先完善 App 基础功能和实际使用闭环，再考虑 AI。登录首屏视觉暂告一段落；账号登录、真实定位到场、现场留话、回复与离场续聊、消息及云端持久化仍需按实际实现和真机结果验收，不能将本机演示视为已上线。

### AI 方向保留，暂不开发

- 核心方向：真实的人留下碎片，AI 帮后来的人找到联系；不是增加一个聊天机器人或用生成内容填充平台。
- 后续候选：从真实留言里发现值得走近的线索，整理地点话题、问答与时间线，提示地点的新回应。
- 基本边界：整理结果可追溯原文；不编造人物、经历、回应或无人留言期间的故事；不通过摘要泄露用户当前无权读取的内容。
- 不要求每个地点都有厚重叙事，保留吐槽、提醒、提问与偶遇的轻量体验。
- 基础闭环可用、有真实内容后再评估和验证，目前不纳入开发范围。

以下为 2026-10-20 的早期小程序工作包参考，不代表当前 App 首页必须采用地图或推进校园建模。

## 第一阶段：完善现有单手机体验

| 任务 | 主要范围 | 完成判定 |
| --- | --- | --- |
| 输入与草稿体验 | 发布页、回复页 | 连续中文输入、中间改字、删除和页面切换不回跳；清空后旧文字不恢复 |
| 地图聚合与热度 | 地图页、逗号资源 | 同一地点多条内容可选择，相近点缩放可展开；大小与数量含义清晰 |
| 卡片与导航适配 | 地图卡片、自定义导航 | 不同屏幕下关闭、返回、切换入口可见；键盘不挡关键操作 |
| 云端热度更新 | `liudaApi` | 部署新计数逻辑，确认同一个人重复回复与作者自回复不会持续增加热度 |
| 现场图文提交闭环 | 发布、详情、本人列表 | 实际发帖成功后能读取、回复、刷新与删除；记录审核和照片实际结果 |

这些任务已有部分源代码实现；手机确认情况和待部署内容见 [部署记录](deployment-status.md) 与 [单手机体验](single-phone-experience.md)。不要把这里的完成判定理解为当前已经通过。

## 第二阶段：一小段真实校园简化街区

目标：选择贸大一栋教学楼和周边一段道路，制作可辨认的简化场景，并与真实位置对应。

| 工作包 | 交付内容 | 与其他工作的关系 |
| --- | --- | --- |
| 范围与参考数据 | 小范围边界、建筑/道路清单、数据或素材来源说明 | 先确定范围，避免多人各做不同区域 |
| 坐标与锚点 | 每个对象的地理坐标、场景坐标、方向和单位 | 建模、GPS 跟随与留言标记使用同一份约定 |
| 简化场景素材 | 建筑轮廓、道路、树和长椅等低复杂度素材 | 遵循自然明亮的街区配色，先保证辨识度 |
| 渲染与加载 | 小程序可加载的场景、资源清理和分块加载方式 | 先确认真机渲染方案，再扩展建筑数量；现有 Canvas 转图片路径是演示实现 |
| GPS 跟随 | 定位到场景位置的转换、视角平滑与回到当前位置 | 视觉平滑不代替原始 GPS 到场权限判断 |

首段场景的完成判定：能认出试点建筑和路口；走动时位置与视角变化可以理解；留言仍属于具体的原地点；记录实际设备上的流畅度和定位偏差。暂不以楼层、桌椅级精准定位为目标。

## 人少时怎么分

- 一位伙伴负责客户端交互、气泡、列表和输入体验。
- 一位伙伴负责云端接口、现场权限、审核与部署。
- 一位伙伴负责校园范围、场景素材与坐标数据；渲染方案由其与客户端负责人一起确定。
- 产品负责人维护范围、优先级和阶段验收。只有两位开发伙伴时，先分客户端与云端，校园素材单独开任务逐项补齐。

每个工作包拆成小 Issue，通过 PR 合并。后续真实校园模型与第一阶段体验完善可以并行，但共享的接口与坐标约定应先写下来。
